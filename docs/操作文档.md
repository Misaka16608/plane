## 3. runner 运行模式

| 目的 | 命令（在 `tools/codex-runner` 下） |
|---|---|

## 4. 配置

### 4.1 runner 全局配置（`tools/codex-runner/.env`）

```ini
PLANE_URL=http://localhost
RUNNER_PORT=9399
WEBHOOK_SECRET=<工作区 webhook 的 secret>
PLANE_ADMIN_TOKEN=<管理员 token，用于创建/管理 webhook>
CODEX_DEFAULT_REPO=WeatherPetUnity   # 全局默认仓库
CODEX_TIMEOUT_MIN=15                 # 单任务 codex exec 超时（分钟）
RUNNER_DRY_RUN=0                     # 1=演练
```

角色 token/user id 自动从 `apps/api/.env` 读取（`CODEX_*_TOKEN` / `CODEX_*_USER_ID`），
无需在 runner `.env` 重复配置。

### 4.2 多项目配置（`tools/codex-runner/projects.json`）

```json
{
  "defaultRepos": {
    "WeatherPetUnity": "D:/_Code/Client/WeatherPet/WeatherPetUnity"
  },
  "projects": [
    {
      "workspace": "workingcatpet",
      "project": "4c9803a4-e542-4213-b04b-57628bc5bee9",
      "defaultRepo": "WeatherPetUnity",
      "repos": {}
    }
  ]
}
```

- `defaultRepos`：全局仓库池，所有项目共用；
- 项目级 `repos`：可覆盖或新增仓库；
- 解析顺序：任务描述"仓库：X" → 项目级 `repos` → 全局 `defaultRepos` → 该项目 `defaultRepo`；
- 没有 `projects.json` 时回退旧单项目模式（`PLANE_WORKSPACE` + `PLANE_PROJECT` + `REPO_*`）；
- 修改配置后需重启 runner 生效。

## 5. 新工作区 / 项目接入（多项目）

1. **加成员**：把 4 个 Codex 账号加入新工作区与对应项目（角色 MEMBER）；
2. **建状态**：在新项目设置里重建同名 10 个状态（见第 6 节清单，名称必须一致）；
3. **配置**：`projects.json` 增加项目条目（仓库路径写本机绝对路径）；
4. **建 webhook**：新工作区创建 webhook 指向
   `http://host.docker.internal:9399/webhook`（见第 7 节），secret 填入 `.env`；
5. **重启 runner**：`node src/runner.mjs`；
6. **验证**：日志出现 `projects configured: N (...)`，且扫描覆盖新项目。

> 项目归属由 issue 自带数据决定，任务描述不需要写"项目"。

## 6. 任务流程（人工操作）

### 6.1 状态清单（每项目一套，顺序即流程）

| 顺序 | 状态 | group |
|---|---|---|
| 1 | 待评估（default） | backlog |
| 2 | 评估中 | unstarted |
| 3 | 待拆分 | unstarted |
| 4 | 拆分中 | started |
| 5 | 待执行 | started |
| 6 | 执行中 | started |
| 7 | 待验收 | started |
| 8 | 验收中 | started |
| 9 | 已完成 | completed |
| 10 | 取消 | cancelled |

### 6.2 触发条件

runner 仅处理「状态名匹配 + 指派人包含对应角色账号」的任务：

| 环节 | 状态 | 指派人 |
|---|---|---|
| 评估 | 待评估 | `codex_eval` |
| 拆分 | 待拆分 | `codex_split` |
| 执行 | 待执行 | `codex_exec` |
| 验收 | 待验收 | `codex_verify` |

### 6.3 任务描述规范

描述里写明即可，格式不强制：

```text
仓库：WeatherPetUnity
需求：……
验收标准：……
```

- 未写"仓库"时用该项目默认仓库；
- 子任务由拆分环节自动创建，直接进入"待执行"；
- 验收 REJECT 会回到"待执行"返工，连续 3 轮转人工（回"待评估"）。

## 7. Webhook 管理

### 7.1 创建（curl，管理员 token）

```powershell
cd D:\_Code\Server\plane
$admin = (Get-Content tools\codex-runner\.env | Where-Object { $_ -match '^PLANE_ADMIN_TOKEN=' }) -replace '^PLANE_ADMIN_TOKEN=',''
curl.exe -s -X POST http://localhost/api/workspaces/workingcatpet/webhooks/ `
  -H "X-Api-Key: $admin" -H "Content-Type: application/json" `
  -d '{"url":"http://host.docker.internal:9399/webhook","issue":true,"issue_comment":true,"is_active":true}'
```

把响应中的 `secret_key` 填入 `tools/codex-runner/.env` 的 `WEBHOOK_SECRET`，重启 runner。

### 7.2 注意事项

- 投递在容器内执行，地址必须用 `host.docker.internal`（不能用 `127.0.0.1`）；
- webhook 连续失败 5 次会被 Plane 自动停用——runner 停机期间若事件积压，
  重新启动 runner 后到工作区设置里把 webhook 重新激活；
- 也可在 Plane 工作区设置界面手动创建/激活 webhook。

## 8. 检查与排障

### 8.1 看日志

```powershell

```

### 8.2 清理残留 in-flight 记录

runner 异常退出可能残留 `state.json` 记录，导致该任务重启后被跳过。清理超过
6 小时的记录：

```powershell
cd D:\_Code\Server\plane\tools\codex-runner
@'
const fs = require("node:fs");
const f = "state.json";
const d = JSON.parse(fs.readFileSync(f, "utf8"));
for (const k of Object.keys(d)) {
  const at = d[k]?.at;
  if (at && Date.now() - new Date(at).getTime() > 6 * 3600 * 1000) delete d[k];
}
fs.writeFileSync(f, JSON.stringify(d, null, 2) + "\n", "utf8");
console.log(JSON.stringify(d));
'@ | node -
```

### 8.3 重置单子上下文

删除 `tools/codex-runner/contexts/<issue-id>.json` 可清掉该单子的会话绑定与返工计数
（下次处理将新开会话）。

### 8.4 常见问题

| 现象 | 处理 |
|---|---|
| `/health` 不通 | runner 未启动；确认 9399 未被占用 |
| 任务不触发 | 检查状态名是否一致、assignee 是否为对应角色账号、`state.json` 是否残留 |
| webhook 不投递 | 到工作区设置重新激活（5 次失败自动停用） |
| 找不到仓库 | 检查 `projects.json` 路径与任务描述"仓库：X" |
| git 提交失败 | 本机 husky 找不到 pnpm，用 `git commit --no-verify` |

### 2026-08-09 · 排查任务卡住并修复 runner 稳定性

- 需求：任务"第一个任务"卡在评估/执行环节，排查并恢复流程。
- 排查发现与修复：
  1. `codex` 命令被 PATH 解析到 WindowsApps 桌面版 Codex 应用，runner 拿不到输出 →
     `.env` 增加 `CODEX_BIN` 显式指向 `.easy-ai` 的 CLI 入口；
  2. `codex exec resume` 在 Windows 上慢/挂起（多次实测 90 秒+无输出）→
     `RESUME_TIMEOUT_MIN=1.5` 独立超时，超时自动降级为新开会话（重注入上下文）；
  3. `worktreeEnsure` 路径比较失败（git 输出正斜杠 vs Windows 反斜杠）→ 归一化后比较；
  4. Plane API `fetch` 无超时可能永久挂起 → `AbortSignal.timeout(15s)`；
  5. 无代码改动任务（纯探索/评论）提交空改动失败 → `hasChanges` 检测，
     无改动时跳过提交直接进入验收；
  6. create 偶发长时间无响应 → `STEP_TIMEOUT_MIN=5` 超时兜底。
- 结果：任务"第一个任务"完整走通 评估→拆分→执行→验收→**已完成**
  （2026-08-09 11:46:20 verify PASS）；单子 worktree 已自动清理；
