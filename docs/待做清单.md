## 1. runner 支持多工作区 / 多项目（已确认需求，未排期，优先级：P0）

### 背景

2026-08-08 与用户确认：现有 runner 是"一实例 = 一个工作区 + 一个项目"的设计，
接入新的工作区/项目只能改配置（旧项目停止自动化）或另起一个 runner 实例。
需要支持多个工作区/项目接入，且互不影响。

### 现状（代码事实）

- `tools/codex-runner/src/config.mjs`：`PLANE_WORKSPACE` / `PLANE_PROJECT` 为单值配置；
- `tools/codex-runner/src/plane.mjs`：所有 API 路径固定为
  `/api/workspaces/<ws>/projects/<p>/...`，启动即绑定；
- `tools/codex-runner/src/flow.mjs`：`states` 状态映射为全局单份，
  触发条件按"状态名 + assignee 是否为对应 Codex 账号"匹配；
- `state.json`（in-flight 记录）与 `contexts/<issue-id>.json`（单子上下文）
  按 issue-id 存储，无项目/工作区维度；
- webhook 为工作区级（`createWebhook` 固定打在配置工作区下），单实例单端口；
- 多"代码仓库"已支持（`REPO_*` 环境变量映射了 3 个仓库），
  但属于"单项目下的多目标仓库"，与多 Plane 项目不是一回事。

### 改造方向（评估用，尚未实施）

已与用户确认的设计决策（2026-08-08）：

1. **形态：单实例多项目**。runner 一个实例服务多个工作区/项目，按 issue 归属路由，
   不做多实例部署；
2. **账号全局共用**：4 个 Codex 角色账号（token/user id 仍在 `apps/api/.env`）
   跨工作区共用，每个工作区/项目里按 Plane 原生成员机制加入（MEMBER）即可，
   runner 不负责权限；
3. **状态名全项目统一**：新项目沿用同一套状态名（待评估…已完成/取消），
   runner 为每个项目**各自拉取并缓存状态映射**（当前 `states` 为全局一份，
   改为 `Map<projectId, states>`）；
4. **项目归属由 issue 自带数据决定**：issue 本身挂在某个工作区/项目下，
   事件进来先识别 payload/API 中的 project 信息 → 定位该项目配置 → 拉该项目状态映射；
   **任务描述不写"项目"**（写了也只作为给 Codex 的提示，路由一律以 issue 归属为准）；
5. **仓库：全局默认池 + 项目级覆盖**：
   - `defaultRepos`（全局池）：所有项目共用，对应现有 `REPO_*`；
   - 项目级 `repos`（可选）：某项目专属仓库集合，可覆盖或新增；
   - 解析顺序：任务描述"仓库：X" → 项目级 repos → 全局池 → 该项目默认仓库
     （每项目可配 `defaultRepo`，缺省回落全局 `CODEX_DEFAULT_REPO`）；
6. **配置形态：独立 JSON + 全局 `.env`**：
   - 全局项保留在 `.env`（`PLANE_URL`、`RUNNER_PORT`、`WEBHOOK_SECRET`、
     `PLANE_ADMIN_TOKEN`、`CODEX_DEFAULT_REPO`、超时、dry-run）；
   - 多项目列表与各项目仓库写入独立配置文件（如 `tools/codex-runner/projects.json`）：
     `[{ workspace, project, defaultRepo?, repos? }]`；
   - 旧 `.env` 单值配置继续兼容 = 单项目模式；
7. **webhook**：每个工作区各建一个 webhook，都指向同一个 runner 端口；
   runner 按事件归属路由（实现时需验证 Plane webhook payload 是否带
   workspace/project 字段；不带则用 URL 路由 `POST /webhook/<workspace>` 或反查 issue）；
8. **`state.json` / `contexts/`**：in-flight 与单子上下文记录增加
   workspace/project 维度，避免跨项目 issue-id 冲突或路由错乱；
9. **分支单号天然区分**：单号前缀用各项目标识（`getProjectIdentifier`），
   `codex/<项目标识>-<序号>` 跨项目不冲突；
10. 兼容现有单项目配置，不破坏 workingcatpet / 项目 4c9803a4 的现有行为。

### 建议验收标准

- 同一 runner 实例可同时处理 ≥ 2 个工作区/项目，互不串扰；
- 新项目接入只需：把 4 个 Codex 账号加为成员 + 重建同名状态 + 配置 webhook，
  即可自动跑完整流程；
- 现有工作区 `workingcatpet` / 项目 `4c9803a4` 行为无回归。

## 2. runner 触发条件：指派人变为"单一指派人"时才处理（已确认需求，未排期，优先级：P2）

### 背景

2026-08-08 与用户确认：当前 runner 只要处理人列表里**包含**对应角色账号就会自动处理
（`assignees.includes(...)`），即使同时指派了别人。需要改为：
多人指派时**先不处理**，待指派人**变为单一**（`assignees` 长度为 1
且为对应角色账号）后才自动处理。

### 现状（代码事实）

- `tools/codex-runner/src/flow.mjs` 的 `stageFor()`：
  `assignees.includes(cfg.roles.<eval|split|exec|verify>.userId)`，
  不检查 `assignee_ids` 数量与唯一性；
- 环节由状态名决定，账号只做"是否在处理人列表"确认。

### 改造方向（评估用，尚未实施）

1. `stageFor()` 判断改为：`assignees.length === 1 && assignees[0] === 对应角色账号`；
2. 非单一指派人（多位处理人、或指派人不是对应角色账号）时**不触发处理**，
   不执行 agent、不改状态、不额外评论；任务保持原状态等待；
3. 依赖现有机制自然恢复：指派人变更会产生 `issue.updated` webhook 事件，
   runner 重新评估后，若此时已是单一指派人则正常开始处理（无需额外改动）。
3. 与第 1 条（多项目支持）改造兼容，不相互冲突。

### 建议验收标准

- 多人指派时 runner 不执行、不改状态、不评论，任务停留在原状态；
- 指派人变为单一且为对应角色账号后（webhook 或扫描触发），自动开始处理；
- 现有工作区 `workingcatpet` / 项目 `4c9803a4` 行为无回归。
