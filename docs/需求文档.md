---

## 1. 目标

把 Plane 当作**任务流程工具本身**来使用；流程中的"执行者"角色由 **Codex**（机器人成员）承担，其余角色与交互保持原生。

一句话：**不是给 Plane 加流程，而是把流程里的人换成 Codex。**

---

## 2. 核心决策（已确认）

1. **不做自定义工作流覆盖层**：不新增流程字段、API、前端面板。此前实现已全部移除（提交 `fd35372`，迁移 `0124` 删除字段）。
2. **Codex = 普通项目成员**：`MEMBER(15)`，非管理员；可被指派为任意环节的负责人（主要是执行者）。
3. **环节 = Plane 自定义状态**；**当前环节负责人 = assignee**；**任务单 = 子任务**（原生父子 issue）。
4. **卡点/退回 = 评论 + @上一级 + 状态直接改回上一环节状态**（无独立"退回中"状态）；**验收 = 验收人把状态推进到"已完成"**。
5. **Codex 配置不进数据库、不进 git**：API token 与代码路径存于 `apps/api/.env`（gitignored）。
6. **本期不做自动化**：不写 runner/脚本轮询；Codex 执行由人触发，回写由 Codex 通过 API 手动完成。
7. **状态推进不设自定义权限校验**：任何项目成员均可推进状态（原生行为），环节纪律靠流程约定与评论留痕约束。
8. **Codex 按流程角色拆分为多个账号**：评估者 `codex_eval`、拆分者 `codex_split`、执行者 `codex_exec`、验收者 `codex_verify`，各自独立 API token；"角色"是账号维度而非 Plane 权限角色，所有账号均为 `MEMBER(15)`。

## 4. 原生流程用法

### 4.1 状态（在项目设置中创建自定义状态）

```mermaid
flowchart LR
    A["待评估"] --> B["评估中"]
    B --> C["待拆分"]
    C --> D["拆分中"]
    D --> E["待执行"]
    E --> F["执行中"]
    F --> G["待验收"]
    G --> H["验收中"]
    H --> I["已完成"]
    H -->|"功能缺陷"| F
    H -->|"拆分/依赖问题"| C
    F -.->|"卡点：评论 + @上一级 + 状态改回"| C
    C -.->|"卡点"| B
    B -.->|"卡点"| A
```

（无独立"退回中"状态；虚线为逐级上抛路径：卡点/退回时评论说明 + @上一级，状态**直接改回上一环节状态**。）

状态分组（Plane 原生 group，决定看板泳道与完成语义）：

| 分组 | 状态 |
|---|---|
| backlog | 待评估 |
| unstarted | 评估中、待拆分 |
| started | 拆分中、待执行、执行中、待验收、验收中 |
| completed | 已完成 |
| cancelled | 取消 |

### 4.1.1 父子任务流转规则（v1.4 确认）

- 拆分者（`codex_split` 或人）在"拆分中"判断任务**是否需要拆分**；
- **不需要拆分**：父任务直接作为流转单元继续流程（拆分中→待执行→…→已完成），不再创建子任务；
- **需要拆分**：父任务**留在拆分者处**（停在"拆分中"），拆分者创建子任务；子任务各自独立走完整流程；
- 全部子任务完成（均已到"已完成"）后，父任务再流转：全部验收通过 → 父任务推进到"**已完成**"；失败/无法达成 → 父任务状态回到"**评估中**"、assignee 改回评估者，重新评估。

### 4.2 日常操作

| 动作 | 原生方式 |
|---|---|
| 发起问题 | 创建 issue |
| 拆分任务 | 拆分者判断是否拆分：不需拆分则父任务直接走流程；需拆分则创建子任务（父 issue 下），父任务停在拆分者处 |
| 指派环节负责人 | 设置 assignee（评估者/拆分者/执行者/验收者按阶段换人） |
| 推进环节 | 当前负责人改状态；**待执行→执行中由执行者自行推进**（Codex 开始执行时推） |
| 卡点/退回 | 评论说明 + `@上一级` + 状态直接改回上一环节状态（如 拆分中→评估中） |
| 验收通过 | 验收人推进到"已完成" |
| 验收返工 | 退回执行者（状态改回"执行中"） |
| 完成问题 | 不需拆分：父任务走完流程，验收人推进到"已完成"；需拆分：全部子任务完成后父任务流转（成功→已完成，失败→返回评估者） |

### 4.3 Codex 执行

1. 按当前环节把对应角色账号指派为负责人：评估中→`codex_eval`、拆分中→`codex_split`、执行中→`codex_exec`、验收中→`codex_verify`（assignee = 对应账号）；
2. 该角色 Codex 用**自己的 token** 通过 API/对话读取任务内容（含 `CODEX_FRONTEND_PATH` 定位代码）；
3. `codex_exec` 被指派且任务状态=待执行时，**自行把状态推进到"执行中"**开始干活，完成后推进到"待验收"并评论说明改动；
4. `codex_verify` 验收：通过则推进到"已完成"；不通过则退回执行者（状态改回"执行中"）或按 4.1.1 返回。

---

## 5. 权限边界

- Codex 只拥有 **MEMBER(15)** 权限：可创建/编辑 issue、评论、推进状态（项目内）；
- 管理员（ADMIN=20）由人担任；Codex 不授予管理员；
- 成员列表已放行 `bot_type=CODEX`，Codex 可被正常指派；
- 状态推进为原生自由行为，任何人（MEMBER 及以上）均可改状态；环节纪律靠流程约定维护，不做自定义校验。
- 四个角色账号权限完全相同（都是 MEMBER），角色差异体现在"指派给谁 + 当前状态"；如需角色级权限差异（如只有验收账号能推进到"已完成"），需引入自定义逻辑，超出当前范围。

## 6. 自动化（v1.5 确认，本期实施）

### 6.1 目标与范围

- **全自动闭环**：runner 自动发现任务 → 自动触发对应角色 Codex → 自动回写状态/评论；
- 自动化环节：**评估（`codex_eval`）、拆分（`codex_split`）、执行（`codex_exec`）**；
- **验收（`codex_verify`）保持人工**：Codex 不验收自己的工作；验收人可借助自动检查（构建/lint 结果）辅助判断。

### 6.2 触发机制（WebHook 为主 + 扫描兜底）

- Plane 工作区配置 **webhook**（事件：issue / issue_comment），推送到 runner 本地监听服务；webhook 带签名与投递日志（Plane 原生支持）；
- **前提改动**：Plane 当前禁止 localhost 回环 webhook 地址，需放开（`WEBHOOK_ALLOWED_IPS=127.0.0.1` + 校验放宽），属自动化基础设施改动；
- **兜底**：runner 启动时 + 空闲 5 分钟做一次全量扫描（按角色+状态查询），防 webhook 丢失/服务重启漏事件；
- **防环**：bot 自身的状态推进也会触发 webhook，runner 按"当前状态+assignee+in-flight"幂等判断，忽略自身引起的无效事件。

### 6.3 环节自动化规则

| 环节 | 触发条件 | runner 动作 |
|---|---|---|
| 评估 | assignee=`codex_eval` 且 state=待评估 | 触发评估 agent（`codex exec`，只读分析）→ 评论评估结论 → 通过则推进到"待拆分"并把 assignee 交给 `codex_split`；不通过/信息不足 → 评论 + 状态回退"待评估" |
| 拆分 | assignee=`codex_split` 且 state=待拆分 | 触发拆分 agent → 判断：不需拆分 → 推进"待执行"并把 assignee 交给 `codex_exec`；需要拆分 → 创建子任务（父任务留在"拆分中"），子任务各自走流程 |
| 执行 | assignee=`codex_exec` 且 state=待执行 | 触发执行 agent → 自行推进"执行中"→ 改代码 + 自检 + 评论 → 提交到本地分支（不 push）→ 推进"待验收"并把 assignee 交给 `codex_verify` |
| 验收 | 人工 | 人工验收；通过 → 推进"已完成"；不通过 → 评论 + 状态改回"待执行"（重新排队执行，不再直接"执行中"） |

- **父任务收尾**（需拆分场景）：runner 检测父任务的全部子任务均到"已完成"后，父任务推进到"已完成"；若存在失败/退回 → 父任务状态回"评估中"、assignee 交回 `codex_eval`。
- **返工统一**：所有回退/返工统一回到"**待X**"状态（待评估/待拆分/待执行），触发条件唯一化，避免 runner 对"X中"状态误判重复执行。

### 6.4 执行与提交（护栏）

- `codex exec` 在**任务指定的子仓库**目录内运行（bglocation / weatherpet-dialogue-editor / WeatherPetUnity），只允许改动该仓库；
- 执行完成后自动 **commit 到本地分支**（分支名 `codex/<任务标识>`），**不 push**，改动留待人工验收；
- 自检按子仓库约定：TS 项目 `tsc/lint`、Gradle `gradle build`、Unity 按项目配置；自检失败视为执行失败；
- 超时保护（单任务最长执行时长，超时按失败处理）；执行日志落盘 `tools/codex-runner/logs/`。

### 6.5 失败处理

- 任一环节失败：runner **评论说明原因 + 状态回退到该环节"待X"**，保留 assignee=对应角色；
- **不自动重试**：避免死循环；人工查看评论后决定重派/修复/改状态。

### 6.6 并发与幂等

- 每个角色同一时刻**只执行一个任务**（串行队列）；
- in-flight 记录（本地状态文件）防止同一任务重复触发；
- 状态本身即锁：推进到"X中"后不再匹配"待X"触发条件。

### 6.7 任务描述规范

- 任务 description 必须写明：**目标子仓库**、需求说明、**验收标准**；
- runner 以"任务名 + description + 评论历史 + 流程约定"拼 prompt；
- 无法定位子仓库的任务 → runner 评论提示补充信息，状态回退"待X"，不执行。

### 6.8 交付物

- runner 工具：`tools/codex-runner/`（独立 Node 脚本，不并入 turbo workspace）；
- Plane 侧小改动：放开 localhost webhook 校验；
- 配置：工作区 webhook（issue/issue_comment 事件）+ `apps/api/.env` 增加 `WEBHOOK_ALLOWED_IPS`。
